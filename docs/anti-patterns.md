# ③ 否决与避坑档案 (Anti-Patterns & Dead Ends)

本文档记录本项目演进历程中被**实测证明存在破坏性隐患并彻底否决的技术方案（暗知识档案）**。
严禁将以下已否决方案重新引入代码库。

---

## 避坑总览表

| 编号 | 否决方案名称 | 致命缺陷现象 | 真实技术根因 | 唯一合法解决方案 |
| :--- | :--- | :--- | :--- | :--- |
| **AP-001** | **Webview 多注入管线未统一收口** | 门禁全绿但插件重装或桌面 App 运行时静默降级为旧版本 | 渲染注入存在多条独立管线（App、IDE、门禁、工具），未统一寻址 | 统一通过 `compat/usage-view.mjs` 解析器收口路径并提供降级回退 |
| **AP-002** | **发布流水线强耦合二进制附件** | 纯文本更新发布时抛出 `KeyError: 'assets'` 致命中断 | 发布脚本硬编码断言本地必须存在 `.zip` 打包产物 | 引入 `--text-only` 模式，解耦文本日志广播与二进制资产检查 |
| **AP-003** | **安装与更新链路硬编码非受控远程地址** | 运行时自动更新与一键安装脚本抛出 HTTP 404 瘫痪 | 硬编码外部网络地址，缺乏容灾降级机制 | 统一指向本仓库主源，并在 Release 资产不可用时自动降级至源码分支归档 |

## 深度剖析 (Deep Dive)

### AP-001：Webview 多注入管线未统一收口
* **现象**：将用量看板实现重构或迁移时，仅更新了 IDE 加载器和单元测试提取点，桌面 App 端仍按旧文件名加载。重新安装插件后，App 界面静默回退至旧版本，而本地测试依然全绿。
* **致命根因**：
  1. 渲染注入存在多条独立物理链路（App 桌面端走 `sidecars/panel/main.mjs`，IDE 走 `ide/main.mjs`，门禁走 `tools/check-*.mjs`）；
  2. 被测代码与门禁同时修改特定文件名，导致**测试与实现互相担保**，未能防御真实运行态。
* **唯一合法解决方案**：
  创建 `compat/usage-view.mjs` 作为系统内唯一的路径裁决处。所有消费者（App 注入、IDE 注入、门禁脚本、资产渲染）必须全部接入 `usageViewPath()` 解析器，严禁自行拼接路径。

---

### AP-002：发布流水线强耦合二进制附件
* **现象**：当仅需要发布版本通知、更新说明或修复轻量脚本时，运行发布工具抛出 `KeyError: 'assets'`，CI 发布流程异常中断。
* **致命根因**：发布脚本无条件断言本地必须存在预打包的 `dist/*.zip` 资产，并在上传后立即校验远程资产列表。
* **唯一合法解决方案**：
  在发布工具（`tools/publish-release.py`）中正式确立 `--text-only` 模式契约。在此模式下豁免所有附件检查，支持纯净的版本状态广播。

---

### AP-003：安装与更新链路硬编码非受控远程地址
* **现象**：在线一键安装（`curl ... | python3`）或后台更新检查抛出未捕获的网络 404 错误，用户无法安装或获取更新。
* **致命根因**：依赖非受控的外部网络路径，且下载逻辑缺乏多级容灾降级。
* **唯一合法解决方案**：
  1. 所有网络寻址统一收敛至本仓库主源；
  2. 安装引导器提供双级容灾：优先尝试拉取 GitHub Release 打包资产；若该 Release 属于纯文本通知而无附件，自动平滑回退至主干源码包（`main.zip`），绝不崩溃。
